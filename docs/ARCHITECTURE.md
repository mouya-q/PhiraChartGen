# 架构说明

## 模块

```
:core   纯 Kotlin/JVM, 不依赖 Android, 可在任何环境跑单元测试
 ├ audio    FFT, 流式降采样, 逐帧特征, 起音检测, BPM 估计, 分析缓存编码
 ├ chart    谱面模型, 难度档位, 生成器
 ├ export   RPE / 官方 JSON / PEC 导出, info.yml, 打包, 兼容性校验
 └ ai       OpenAI 兼容客户端, 重试与回退, 分段建议解析
:app    Android 应用
 ├ media    系统解码, WAV 写入, 封面生成, 流水线
 ├ data     设置, Keystore 密钥保管, 诊断日志
 └ ui       Miuix 界面, 预览渲染
```

`:app` 依赖 `:core`, 反向不成立. 所有与算法, 格式相关的逻辑都在 `:core`

## 数据流

```
音频 URI
 → MediaExtractor + MediaCodec 解码为 16 位 PCM (按块)
 → 混合为单声道, 面积加权降采样到 22050 Hz (按块)
 → SpectrumStream: 1024 点 FFT, 步长 256, 逐帧特征
      三频段对数频谱流, 响度, 频谱质心, 4 kHz 以内谱线
 → 局部归一化得到起音包络 → 峰值检测 → BPM 与相位估计
 → AnalysisResult (逐帧数组, 可缓存到磁盘)
 → [可选] AI 分段密度建议
 → ChartGenerator 按难度档位选取音符, 分配类型, 轨道, 判定线
 → Chart (与格式无关)
 → RpeExporter / OfficialExporter / PecExporter + info.yml → zip
 → PackValidator 校验导出的文件
```

任何阶段都在后台线程执行. 解码和分析以固定大小的块推进, 内存只与逐帧特征数组有关 (约每分钟音频 4 MB, 收尾阶段峰值约翻倍), 因此限制时长为 15 分钟

## 生成算法要点

- **起音**: 对数幅度谱的半波整流差分, 分低 (250 Hz 以下), 中, 高 (2.5 kHz 以上) 三个频段, 去除滑动均值后按局部能量归一化
- **BPM**: 起音包络自相关加先验, 再用最强起音对 BPM±3 与相位做细对齐. 对齐用半拍网格, 所以相位在半拍内是可靠的
- **时间校准**: 峰值时间加固定的 0.75 帧长偏置, 该值由合成数据实测得到
- **选取**: 每 3 秒一个窗口, 按目标密度与该窗口响度取最强起音, 不足时在半拍网格补点. AI 建议只作为密度倍率
- **类型**: 长按来自新出现且持续存在的谱线, 滑动来自强且偏亮的重音, 拖动来自密集连打, 同时按键只在 IN 与 AT
- **轨道**: 以频谱质心偏好轨道, 加上避免连续重复, 限制跳跃, 长按期间占用轨道
- **难度数值**: 由平均密度, 95 分位密度, 同时按键与拖动比例估算

## 谱面时间与 offset

内部所有时间是音频时间轴上的秒. 导出时用一个**前导拍**把第一拍对齐到音乐中的实际位置: BPM 列表第 0 项让第 0 到 1 拍恰好覆盖到第一拍时刻, 之后使用估计的 BPM. 这样谱面文件本身的 offset 保持 0, 避免 RPE 与 info.yml 两处 offset 符号相反带来的歧义. info.yml 的 offset 只承载用户在设置里手动校准的延迟

音符以精确时间放置. 靠近网格 (默认 35 毫秒内) 的音符才吸附到网格, 因此现场演奏造成的节拍漂移不会累积误差

## 决策记录

### ADR-1 起音与节拍分析自研, 不引入第三方音频库
- 候选: TarsosDSP (GPL-3.0), aubio (GPL-3.0), FFmpeg (LGPL, 体积大), librosa (Python)
- 决定: 自研 FFT 与谱流, 约 300 行
- 理由: GPL 库会迫使整个应用采用 GPL; FFmpeg 会显著增加包体与许可证负担; 自研代码可在 JVM 上直接单测
- 代价: 算法质量需要自行维护, 目前只做了合成数据验证

### ADR-2 解码使用系统 MediaCodec
- 理由: 无额外依赖与许可证问题, 覆盖常见格式
- 代价: 不同设备支持的编码略有差异, 失败时给出明确提示

### ADR-3 核心逻辑放在纯 JVM 模块
- 理由: 单元测试快, 可在 CI 无模拟器运行, 边界清晰

### ADR-4 单一恒定 BPM, 精确时间加软吸附
- 理由: 单一 BPM 能覆盖绝大多数流行音乐, 且 Phira 各格式都能稳定表达; 变速曲目留作后续
- 代价: 变速曲目只有音符时间准确, 节拍线不会随之变化

### ADR-5 RPE 为推荐格式
- 理由: 覆盖事件, 控制字段最完整, 社区谱面最常见
- 官方 JSON 与 PEC 保留给有特定需求的用户, 验证状态见 VALIDATION.md

### ADR-6 密钥使用 Android Keystore AES-GCM
- 理由: 密钥材料不可导出, 不依赖已不再推荐的 security-crypto 库
- 密文与初始向量以 Base64 存入私有 SharedPreferences, 不参与系统备份 (allowBackup 为 false)

### ADR-7 AI 只上传统计数据并只返回密度倍率
- 理由: 最小化隐私影响, 并保证模型输出无论多糟糕都不会破坏谱面结构 (倍率被限制在 0.3 到 1.6)
- 任何错误统一回退离线生成

### ADR-8 Miuix 经单文件封装, 玻璃效果使用 Compose 自带模糊
- 理由: Miuix 仍处于实验阶段, 接口可能变动, 集中封装降低升级成本; 背景模糊使用 Compose 的 `Modifier.blur`, 不额外依赖模糊库
- 代价: Android 12 以下系统上 blur 不生效, 退化为压暗封面

### ADR-9 音频打包策略
- MP3, OGG, WAV 原样放入谱面包, 其他格式转为 16 位 PCM WAV
- 理由: 避免重复编码损失, 且 Phira 接受这三种格式
- 代价: WAV 体积较大. MP3 在 Phira 中可能有解码延迟, 用谱面延迟校准
